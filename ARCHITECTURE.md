# data-pipeline-core — Architecture

A reusable Python SDK for building GCP data-ingestion pipelines. It provides the
**plumbing** that every solidly-engineered pipeline needs (worker runtime,
resilience, observability, storage adapters) so that a new pipeline is "just"
three things to write: the **ingestion logic** (the worker's `fetch()`), the
**transform logic** (`transform()`, parsing/normalization — optional), and the
**interface** that presents the stored data.

## 1. Problem & goal

Multiple projects (Polytricks (French politics); `proba-markets-analysis` (sports-betting markets); future ones) share the same skeleton:

```
ingest  →  land (raw)  →  transform  →  store (curated)  →  expose
```

on GCP, with stateless workers and serious observability. What genuinely differs
between projects is the **fetch logic**, the **transform logic**
(parsing/normalization), and the **interface** (what is done with the data).
Everything else (the runtime, the staging/handoff between stages, resilience,
observability) is the engineered plumbing, re-implemented each time today.

**Goal:** make that plumbing a library import, not a rewrite. A new pipeline
should start "hollow", with only `workers/source.py` and the interface left to
write; everything else is `import data_pipeline_core` + `terraform apply`.

---

## 2. Design principles

- **Contract-driven.** The SDK owns the run loop; the project fills typed
  `Protocol` slots (`Source`, `Sink`). Inversion of control: the framework calls
  your code, not the other way around.
- **Only the generic goes in.** A mechanism is shared; its values are not.
  Project-specific thresholds become **config defaults**, never hard-coded
  constants. Anything referencing a bookmaker, an odds value, a canonical entity,
  or a strategy stays in the consuming project.
- **Config over forking.** Behaviour varies by configuration (e.g. Polytricks
  disables the proxy, keeps retry/jitter), not by editing the SDK.
- **Serverless-native.** Workers are short-lived Cloud Run Jobs. The SDK assumes
  start → work → push metrics → exit, not long-running scrape targets.
- **Ingest and transform are decoupled.** Ingest workers do the minimum — fetch
  and land the *raw* payload — then hand off via a staging boundary (raw GCS
  bucket or Pub/Sub). Transform workers consume the raw data for
  parsing/normalization. This keeps the connection/IP-exposure window short, makes
  raw data an immutable, replayable source of truth (a parser bug never loses
  data), and lets heavy transforms retry and scale independently of fetching.
  Both are the same `WorkerApp`, only wired with different Source/Sink. Simple
  pipelines may transform in-process in a single worker; the split is a wiring
  choice, not a fork.
- **Stable observability surface.** A fixed set of metric series (names + labels)
  so Grafana dashboards are shared across all consumers.
- **Lean on proven libs.** dlt for the load layer (schema inference, incremental,
  destinations); the SDK adds only what no library packages already provides (runtime,
  resilience, GMP push).

## 3. The stable / variable boundary

| Layer | Provided by SDK / modules (stable) | Written per project (variable) |
|---|---|---|
| Worker runtime | lifecycle, config, structured logging, shutdown | — |
| Ingestion | HTTP client, IP guard, proxy, retry/jitter, dedup | **the `fetch()`** (scraper/API), thresholds |
| Staging / handoff | raw-landing Sink + Source (GCS raw / Pub/Sub) | — |
| Transform | run loop, the `Transform` slot, retries | **the `transform()`** (parsing/normalization) |
| Storage | GCS / Postgres / Redis adapters (via dlt) | **schema / canonical model**, mapping |
| Observability | Prometheus instrumentation, GMP push, standard series | a few business metrics |
| Infra | Terraform modules | variable values |
| Interface | — | **everything** (Next.js, Streamlit, API) |

The right-hand column is the business logic. The left-hand column is this SDK
(plus the infra modules and template — see §4).

## 4. System context — three artifacts, three repos

```
data-pipeline-core/        # the Python SDK (this repo)
data-pipeline-infra/       # reusable Terraform modules
data-pipeline-template/    # cookiecutter scaffolding
```

A business project is a fourth repo, generated by the template, depending on the
SDK and calling the infra modules.

- **SDK** — the runtime + resilience + observability + storage adapters described
  here. Versioned (SemVer), published to a private Artifact Registry.
- **infra** — Terraform modules for `cloud-run-job` (job + Scheduler + Pub/Sub +
  IAM), `warehouse` (GCS + Cloud SQL + Memorystore), `observability` (GMP +
  Grafana datasource + dashboards-as-JSON). Grafana dashboards are versioned, not
  hand-rebuilt.
- **template** — `cookiecutter` that emits a hollow project: `workers/source.py`
  to fill, `workers/main.py` already wired, `infra/main.tf` pre-filled, an
  interface placeholder (Next.js or Streamlit), and CI/CD.

```
            ┌─────────────────────┐
            │  data-pipeline-core │  (import, pinned ==X.Y.*)
            └──────────┬──────────┘
                       │
  data-pipeline-template ──emits──► business project ──calls──► data-pipeline-infra
                                     (source.py + interface)
```

│   └── circuit_breaker.py  # per-source state, configurable halt (default 15 min)

## 6. The core contract

The SDK defines three Protocols; a project implements `Source` and (when it
parses/normalizes) `Transform`. The framework provides the loop.

```python
# storage/protocols.py
from typing import Protocol, Iterable, Any

Record = dict[str, Any]

class Source(Protocol):
    """Implemented per project: THE ingestion business logic."""
    name: str
    def fetch(self, ctx: "RunContext") -> Iterable[Record]: ...

class Transform(Protocol):
    """Optional, per project: parsing / normalization of raw records."""
    def transform(self, record: Record, ctx: "RunContext") -> Iterable[Record]: ...

class Sink(Protocol):
    def write(self, records: Iterable[Record]) -> "WriteResult": ...
```

```python
# runtime/app.py — provided, identical everywhere
class WorkerApp:
    def __init__(self, source: Source, sink: Sink,
                 transform: Transform | None = None,
                 settings: Settings | None = None): ...
    def run(self) -> int:
        """
        Wraps source.fetch() → (transform, if wired) → sink.write() with, for free:
          - RunContext (run_id, structured logger, redis, clock)
          - IP guard (Redis sliding window → mode → proxy when needed)
          - per-source circuit breaker (halt on repeated 429s)
          - standard metrics (see §8)
          - GMP push at end of run, clean exit code
        """
```

The same `WorkerApp` covers both archetypes — the difference is only the wiring.

```python
# Ingest worker: fetch and land raw, nothing more.
WorkerApp(
    source=LegifranceSource(),                     # the project's fetch logic
    sink=raw_landing_sink(channel="laws-raw"),     # GCS raw bucket / Pub/Sub
).run()

# Transform worker: consume raw, parse/normalize, store curated.
WorkerApp(
    source=raw_landing_source(channel="laws-raw"),
    transform=LawParser(),                         # the project's transform logic
    sink=dlt_sink(dataset="laws", destination="filesystem"),  # GCS parquet
).run()

# Simple pipeline: do it all in one worker (no staging).
WorkerApp(source=LegifranceSource(), transform=LawParser(),
          sink=dlt_sink(dataset="laws", destination="filesystem")).run()
```

## 7. Runtime model

Workers are stateless Cloud Run Jobs triggered by Cloud Scheduler (baseline) and
Pub/Sub (priority/high-frequency). `WorkerApp.run()` is the single entry point and
owns the lifecycle:

1. Build `RunContext` — run id, structured (JSON) logger, config, clock, Redis.
2. Iterate `source.fetch(ctx)`; if a `Transform` is wired, apply it; stream
   records to `sink.write()`.
3. Each outbound request goes through the instrumented HTTP client (retry, jitter,
   UA rotation), the IP guard, and the circuit breaker.
4. On SIGTERM, shut down gracefully (Cloud Run Jobs can be preempted).
5. On exit, push metrics to GMP and return a clean exit code.

**Two archetypes, one loop.** An *ingest worker* (`Source` → raw-landing `Sink`)
and a *transform worker* (raw-landing `Source` → `Transform` → curated `Sink`)
are the same `WorkerApp`, differing only in wiring. Both reuse the same lifecycle,
logging and metrics; the HTTP client / IP guard / proxy only engage on the stage
that makes outbound requests (ingest). The staging boundary (raw GCS / Pub/Sub)
is what decouples them — see §2 and §10.

The project never writes lifecycle, logging, metrics, or resilience code, it only
yields records from `fetch()` (and, optionally, `transform()`).

## 8. Observability

Two tracks, deliberately separated:

- **Operational metrics (worker health)** — `prometheus_client` instrumentation,
  **pushed** at end of run (workers are short-lived, so push not scrape) via
  GMP remote-write/OTLP, with a PushGateway fallback. Visualised and alerted in
  Grafana Cloud.
- **Analytical KPIs** (events tracked, odds dynamics, P&L) — **not** in
  Prometheus; computed from the GCS/DuckDB warehouse and surfaced in the project's
  own interface (Streamlit/Next.js). Out of scope for the SDK.

Standard series (stable names + labels, so dashboards are shared):

| Series | Meaning |
|---|---|
| `worker_up` / heartbeat | liveness per worker and per source |
| `worker_runs_total{status}` | completed runs by outcome; `sum` = runs, `status="failure"` = errors — aggregatable per day/week/month |
| `records_written_total`, `bytes_written_total` | volume written to the sink (throughput + storage footprint accrued over time) |
| `request_rate`, `http_status_total{code}` | throughput and 429 counts |
| `ingestion_lag_seconds` | time since last successful tick per source |
| `circuit_breaker_state{source}` | 0 = closed, 1 = open |
| `proxy_usage_ratio` | share of requests routed via proxy |

The **technical dashboard** over these series (runs, in-flight, errors, storage,
per day/week/month) is a Grafana dashboard-as-JSON owned by `data-pipeline-infra`
(alongside the GMP/Grafana provisioning that deploys it); the SDK owns only the
series. `bytes_written_total` is populated when a sink can report volume cheaply
(raw landing); the dlt sink reports rows only, so its bytes read 0.

## 9. Resilience & adaptive ingestion

All of these are SDK mechanisms with **config-driven** parameters; defaults come
from the betting architecture but every value is overridable.

- **HTTP client**: retries with jitter, User-Agent rotation.
- **Circuit breaker**: per-source; on repeated `429 Too Many Requests` it opens
  and halts that source for a configurable cooldown (default 15 min) to protect IP
  reputation, then flips `circuit_breaker_state` to 1.
- **IP guard**: a Redis sliding-window counter per source drives a mode switch:

  | Mode | Default threshold (req/hr) | Action |
  |---|---|---|
  | Safe | `0 < N < 300` | direct connection |
  | Warning | `300 ≤ N < 500` | increase jitter, randomize UA |
  | Aggressive | `N ≥ 500` | route all traffic through proxy |

- **Proxy middleware** — SaaS proxy (e.g. Oxylabs) wrapped in httpx, activated by
  the IP guard or a volatility trigger.

A low-frequency consumer (Polytricks, daily) can disable the proxy entirely and
keep only retry/jitter — by config, without touching the SDK.

## 10. Storage

The SDK exposes storage behind the `Sink` Protocol and leans on **dlt** for the
load layer (schema inference + evolution, incremental loading, destinations):

- **Raw landing (bronze)** — immutable raw payloads in a GCS raw bucket or
  Pub/Sub, written by ingest workers (`raw_landing_sink`) and read by transform
  workers (`raw_landing_source`). The replayable source of truth before parsing.
- **Cold storage (curated)** — Parquet in GCS (analytics source of truth, queried
  with DuckDB), written by transform workers.
- **Hot storage** — Postgres (Cloud SQL) for metadata and latest state, via dlt
  upsert.
- **Cache** — Redis (Memorystore) for latest snapshots and the IP-guard counters.

Idempotency comes from deterministic record IDs (`storage/ids.py`): re-running a
worker does not duplicate rows.

The **canonical data model and schema are project-owned**: the SDK moves and
stores records but does not define the betting `CanonicalEvent`/`Observation`/
`MarketState` or any business schema.

## 11. Versioning & dependency contract

- **SemVer**, strict. Any breaking change to the contract (`Source`, `Sink`,
  `WorkerApp`, public signatures) is a **major** bump.
- Consumers pin `data-pipeline-core==X.Y.*` (minor fixed, patch floating).
- During co-development the SDK stays in `0.x` and consumers depend on it via an
  editable local path; on release the override is dropped and a version is pinned
  (see the spec §7 for the workflow).
- **Inclusion rule:** only what is *literally* identical across projects enters
  the SDK. When in doubt, leave it in the project and promote it once a second
  real usage confirms the shape.

## 12. Out of scope (stays in consuming projects)

- Canonical data model and entity resolution (e.g. "Marseille" ↔ "OM").
- Margin/overround normalization, feature store, backtesting, modelling.
- The UI / research layer (Streamlit, Jupyter, Next.js) and analytical KPIs.
- Concrete `fetch()` and `transform()` logic and numeric thresholds (the latter
  become config defaults, not SDK constants).
